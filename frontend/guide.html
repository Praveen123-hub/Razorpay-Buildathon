The Big Picture

What is this Project?

This project is a Multi-Agent E-Commerce Platform connecting two merchant storefronts ShopNest and CartWave with an intelligent conversational shopping assistant (Agent 1) and an automated sales improvement agent (Agent 2).

Why Now:
NPCI’s UAP and the global protocol race (ACP, AP2, x402) make agent-to-agent commerce the open problem of the year, and Razorpay’s in-app pilots are already live.
The Bar:
Every money action explainable, bounded and gated. Show the audit trail and one failure handled gracefully.

Instead of manually browsing multiple websites and guessing which store has the best deal or right size, users simply talk to the AI in plain English. The platform compares prices, checks live stock, suggests compatible add-ons, and completes checkouts with test payments.

Authentication & Database Architecture

How user accounts, security salts, addresses, and order history are stored.

Security Core

Password Security & What is a "Salt"?

Passwords are never stored in plain text. Instead, they are hashed using PBKDF2-HMAC-SHA256 with 100,000 iterations and a unique 16-byte random Salt.

What is Salt?
A Salt is a random string added to the password before hashing. Even if two users choose the exact same password (e.g., Password123), their stored hashes will look completely different, protecting against hackers and precomputed Rainbow Tables.
Keys Summary

Primary Keys vs Foreign Keys

Across the entire SQLite database (app.db), there are exactly:

  • 4

    Primary Keys (PK)

    users.id, user_sessions.id, user_addresses.id, user_orders.id (Unique ID for each row).

  • 3

    Foreign Keys (FK)

    All 3 FKs point back to users.id to identify which user owns that address, session, or order.

The 4 SQLite Database Tables

Table Name Primary Key Foreign Key Stored Details
users id (INTEGER) None User's name, email (unique lowercase), 100,000-iteration password hash, random 16-byte salt, creation date.
user_sessions id (INTEGER) user_id → users.id 32-byte secure bearer token, expiration timestamp (valid for 30 days).
user_addresses id (INTEGER) user_id → users.id Recipient name, phone, address lines 1 & 2, city, state, postal PIN code, country.
user_orders id (INTEGER) user_id → users.id Order ID, merchant name, total INR amount, payment status, items JSON list, and shipping address snapshot.

Finite State Machine

1. What is a Finite State Machine (FSM)?

A Finite State Machine (FSM) is a behavioral design pattern and mathematical model of computation.

  • How it works: A system can only be in exactly one state at any given moment out of a predefined, finite set of states.
  • State Transition: The system moves from one state to another (transition) only when a specific condition, trigger, or user input occurs (event).
  • Deterministic: For any given current state and user input, the next state is 100% predictable and guaranteed.

2. Why FSM is Used in Agent 1

Why not let an AI Model talk freely without an FSM?
If a conversational e-commerce bot is purely open-ended, it can:
  • Forget to ask for shoe size before carting.
  • Add items to the cart without user permission.
  • Hallucinate that an order is paid when it isn't.
  • Skip vital stock or price checks.

The 6 Core States (Nodes) in Agent 1:

S1

COLLECTING_REQUIREMENTS

Asks the user for missing info (product name, size, color, budget, priority). Once all slots are filled → transitions to State 2.

S2

AWAITING_MAIN_CART_CONFIRMATION

Presents the winning offer. If User says Yes → transitions to State 3 (or 4). If No → back to State 1.

S3

AWAITING_COMPLEMENTARY_CART_CONFIRMATION

Presents cross-sell recommendation from Agent 2. Whether User says Yes or No → transitions to State 4.

S4

AWAITING_ORDER_CONFIRMATION

Shows full cart summary with total INR. If User says Yes → creates payment order and goes to State 5.

S5

AWAITING_PAYMENT

Waits for Razorpay checkout to finish. Once payment signature is verified → transitions to State 6.

S6

READY_FOR_PURCHASE (Terminal)

Deducts live inventory, logs merchant order, saves into SQLite database, and clears cart.

Deterministic Decision Logic

Mathematical Scoring Engine & Formulas

Offers are scored on a scale from 0.0 to 1.0 using three clear mathematical steps:

1. Price Score = (Max Price - Product Price) / (Max Price - Min Price)
2. Rating Score = Product Rating / 5.0
3. Value Score = (Price Weight × Price Score) + (Rating Weight × Rating Score)
Priority Mode Price Weight (W_P) Rating Weight (W_R) Goal
cheapest 90% (0.90) 10% (0.10) Gives heavy advantage to lowest price.
highest_rated 10% (0.10) 90% (0.90) Gives heavy advantage to top customer reviews.
best_balance 50% (0.50) 50% (0.50) Equal balance between price and quality rating.

Real Example: Smartwatch Search (Cheapest Priority)

Suppose ShopNest offers a Smartwatch for ₹3,500 (Rating 4.8★) and CartWave offers it for ₹3,000 (Rating 4.2★):

ShopNest Offer

Price: ₹3,500 (Max Price) | Rating: 4.8★

Price Score = (3500-3500)/500 = 0.0
Rating Score = 4.8 / 5.0 = 0.96
Value Score = (0.90 × 0.0) + (0.10 × 0.96) = 0.096

CartWave Offer

Price: ₹3,000 (Min Price) | Rating: 4.2★

Price Score = (3500-3000)/500 = 1.0
Rating Score = 4.2 / 5.0 = 0.84
Value Score = (0.90 × 1.0) + (0.10 × 0.84) = 0.984

WINNER (0.984 > 0.096)

Why this LLM? Lightweight, sub-500ms speed, and strictly follows prompt rules to write natural 1-2 sentence recommendation copy without hallucinating discounts.

Tools

Math Formula

Co-Purchase Probability Formula: P(B | A)

Agent 2 looks at all historical orders from the merchant and calculates:

P(B | A) = (Orders containing BOTH Product A and Product B) / (Total orders containing Product A)
Example: If 50 people bought Running Shoes (Product A), and 35 of those orders also included Athletic Socks (Product B), the probability is 35 / 50 = 70%.

The 2-Stage Category & Semantic Compatibility Validator

1

Category Cluster Matching (Hard Filter)

Ensures products belong to matching domains (e.g. Footwear goes with Footwear Accessories; never with Kitchenware).

2

Dense Semantic Similarity (AI Filter)

Uses vector embeddings to ensure descriptions match functionally (e.g., shoe polish matches leather shoes, not sneakers).

Local Semantic Search & Vector Embeddings

How products are searched by meaning instead of exact keywords without heavy database infrastructure.

Embedding Model

all-MiniLM-L6-v2

Runs 100% locally on CPU using HuggingFace and PyTorch. Converts each product's title, category, description, and specs into a 384-dimensional vector (a list of 384 numbers).

Vector Dimension: 384
Total Stored Vectors: 100 (50 for ShopNest + 50 for CartWave)
Memory Footprint: < 150 Kilobytes RAM

Chunking

I have intentionally not used any text chunking here. In document search systems (like long PDF search), documents are sliced into 500-word chunks. But in our e-commerce catalog, each product is already concise (around 40–80 words), so 1 complete product directly maps to 1 single vector. If I had applied chunking, it would split the product's title away from its available sizes and colors, which would break semantic search accuracy.

Architecture Decision

Why NO External Vector Database?

Our platform contains 50 products per merchant (100 product vectors in total). For this catalog size(Just 100 vectors), setting up and connecting to an external Vector Database (like Pinecone, Milvus, or Chroma) introduces unnecessary complexity, network latency, and cloud costs and also it occupies very less space.

  • 1

    Ultra-Fast (< 0.05 ms vs 100 ms)

    NumPy dot product on 100 vectors directly in CPU memory takes microseconds, whereas external databases waste time over internet calls.

  • 2

    Zero Infrastructure Cost & Complexity

    No external database subscriptions, no Docker containers, and no complex cluster maintenance.

  • 3

    100% In-Memory Sync

    Vectors stay perfectly synchronized with the local merchant catalogs with zero synchronization delay.

Trust Layer & The 7 Security Guardrails

The protective firewall ensuring AI models cannot hallucinate prices or modify orders without consent.

Security First

Why Do We Need a Trust Layer?

Large Language Models are probabilistic text generators. If you let an AI write directly to your database, it could invent a 90% discount, sell products that have zero stock, or charge cards without authorization. The Trust Layer intercepts every action with 7 non-negotiable rules:

Guardrail 1

Price Consistency & Anti-Tamper

Compares the offer price against the merchant's live catalog. If an AI hallucinates a discount, it is blocked with PRICE_MISMATCH.

Guardrail 2

Real-Time Inventory Check

Verifies that available stock is greater than or equal to the requested quantity (Stock ≥ Quantity). Prevents overselling with PRODUCT_OUT_OF_STOCK.

Guardrail 3

Explicit User Consent

Requires the user to explicitly say "Yes" before any add-on recommendation enters the cart. Blocks automatic carting with USER_DECLINED.

Guardrail 4

Merchant & Product Identity

Confirms the merchant is strictly shopnest or cartwave and that the product ID exists. Blocks fake names with MERCHANT_NOT_FOUND.

Guardrail 5

Pre-Checkout Cart Consistency

Audits every item in the cart simultaneously right before generating the payment invoice to ensure stock hasn't depleted while chatting.

Guardrail 6

Delivery Address Completeness

Ensures recipient name, phone, street, city, state, and pincode exist in database before allowing checkout initialization.

Guardrail 7

Cryptographic Payment Signature & Idempotency

Computes HMAC-SHA256 to verify that payment confirmations genuinely originate from Razorpay servers and prevents duplicate charges on repeated clicks.

8. AP2 (Agent Payment Protocol) & UAP (Universal Agent Protocol)

Standardized machine-to-machine agent communication, discovery, and bounded cryptographic payment delegation.

UAP/1.0 Standard

Universal Agent Protocol (UAP)

UAP is an interoperable protocol (aligned with NPCI agentic standards) that standardizes how autonomous and semi-autonomous AI agents discover each other, authenticate identities, and exchange structured intent envelopes across diverse merchant ecosystems.

Standard Agent Envelope Schema:
Every inter-agent message between Agent 1 (Buyer) and Agent 2 (Merchant Sales) is encapsulated in a signed UAPMessageEnvelope. 
{
  "protocol_version": "UAP/1.0",
  "message_id": "uap_msg_7f8c9b2a1e0d3f45",
  "sender_id": "agent1_buyer",
  "recipient_id": "agent2_shopnest",
  "intent": "RECOMMEND_CROSS_SELL",
  "timestamp": "2026-09-03T10:15:30Z",
  "payload": {
    "merchant": "shopnest",
    "product_id": "SHOE_001",
    "quantity": 1
  },
  "signature": "hmac_sha256_e82f1b409d..."
}
  • 1

    Agent Discovery Manifest

    Hosts /.well-known/agent.json declaring active roles (BUYER_ORCHESTRATOR, MERCHANT_SALES_OPTIMIZER), endpoints, and supported intents.

  • 2

    Cryptographic Envelope Non-Repudiation

    Guarantees inter-agent integrity via HMAC-SHA256 signatures over canonical message fields.

AP2/1.0 Standard

Agent Payment Protocol (AP2)

AP2 establishes a secure, bounded financial interface for AI agents. Instead of sharing raw payment credentials with AI models, AP2 issues Cryptographically Bounded Delegation Mandates and verifiable settlement claims.

The 5 AP2 Mandate Constraints:
1. Hard Maximum Spending Ceiling (₹ Max Bound)
2. Strict Merchant Scope Whitelist (e.g. ShopNest, CartWave)
3. Expiration Time Window (e.g. 60 min validity)
4. SHA-256 Cart Contents Fingerprint (Anti-tampering)
5. Cryptographic Signature & Single-use Settlement 
{
  "mandate_id": "ap2_man_9a4f61e82b7c4d30",
  "agent_id": "agent1_buyer",
  "authorized_merchants": ["shopnest"],
  "max_amount": 2400,
  "currency": "INR",
  "expires_at": "2026-09-03T11:15:30Z",
  "cart_hash": "a4d3f09b82e1c7...",
  "status": "AUTHORIZED",
  "signature": "hmac_sha256_7b82..."
}
  • 3

    Trust Layer Guardrail #8

    Verifies mandate validity, budget ceiling, cart hash, and active expiry before payment gateway handoff.

  • 4

    Verifiable Settlement Receipt

    Generates immutable AP2SettlementReceipt containing transaction receipt hash upon Razorpay completion.
